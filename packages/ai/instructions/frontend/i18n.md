# i18n conventions

## Components without an i18n library

For components meant for any stack.

- No i18n library in the package. The app gives an adapter of this type, which the package copies verbatim into its
  `src/api/i18n.ts` (with `TextParams`). A change is made here first, then in every copy in the same step: the copies
  stay identical, so one adapter of the app fits every package (TypeScript compares the types by their shape).
  ```ts
  /**
   * The app's i18n system, as a library sees it. The app writes one adapter and gives it to every library that has
   * texts.
   */
  interface I18nAdapter {
    /** The current locale, e.g. `'de-DE'`. */
    currentLocale: () => string;
    /**
     * The translation of a key in the current language, or `null` when there is none: then the library uses its own
     * English text. `namespace`: the library's (its name in camelCase, e.g. `'formValidation'`), one the app names for
     * its own keys, or `null` for the app's default namespace. `params`: the raw values (numbers, dates), `null` for
     * none; the translation formats them and picks the plural (by `count`).
     */
    translate: (
      namespace: string | null,
      key: string,
      params: Readonly<Record<string, unknown>> | null,
    ) => string | null;
    /** Reports a change of the language; returns the function that ends the subscription. */
    onChange?: (listener: () => void) => () => void;
  }

  /**
   * The values of each text of a library's English texts (functions of their values and the locale):
   * `TextParams<typeof EN>` gives `{ 'number.min': { min: number }, … }`.
   */
  type TextParams<T> = { [K in keyof T]: T[K] extends (params: infer P, locale: string) => string ? P : never };
  ```
- `translate` only translates: `null` when there is no translation, and the library uses its own text (its English
  one, a humanized name, a literal text). So the adapter never sees a default, and the library knows for sure when a
  translation is missing (e.g. to warn). `null`, not `undefined`: explicitly no value, like `getAttribute()`.
  - No `hasTranslation`: the adapter checks cheaply inside `translate` (e.g. i18next's `exists`); a separate check
    would be two calls and two lookups.
- Without an adapter: English texts and `en-US` formatting, always. The page's language (`<html lang>`) and the
  browser's are never read: the language comes only through the adapter.
- How a library takes the adapter is its own API; there is no shared type for it.
  - A React library: a hook option, `useI18n?: () => I18nAdapter`, called on every render. It covers a global
    instance (`useI18n: () => i18nAdapter`) and an i18n that only exists inside React (a provider, a library with
    only a hook), built there and kept the same object while nothing changes:
    ```ts
    useI18n: () => {
      const translator = useXyzTranslator();
      return useMemo(() => toAdapter(translator), [translator]);
    };
    ```
  - A component the app renders itself (a provider): the adapter as a prop (`config={{ i18n }}`), which the app
    builds with its own hooks; a new adapter object counts as a change.
  - A custom element: a value in its class config, `createXyzClass({ i18n: i18nAdapter })`, the same adapter for
    every element of the class. Its React wrapper takes only the hook (`useI18n`, as above) and hands the adapter to
    its own element internally.
  - The library subscribes to `onChange` while it is mounted (an element: while connected), and renders its texts
    again.
- The library's texts: only English (`en-US`), as plain functions of the values and the locale, the master of its
  texts (`src/texts/en.ts`), typed by `TextParams<typeof EN>`.
  ```ts
  const EN = {
    'number.min': ({ min }: { min: number }, locale: string) => `The value must be at least ${number(min, locale)}.`,
    'string.min': ({ count }: { count: number }, locale: string) =>
      `Please enter at least ${number(count, locale)} ${count === 1 ? 'character' : 'characters'}.`,
  };
  ```
  - `locale`: the adapter's (`en-US` without one), so the formatting follows it (`en-GB` dates, `de-CH` numbers).
  - Only what ICU can express: values, numbers and dates formatted with `Intl`, and English's two plural forms
    (`count === 1`). No other logic.
  - The params go raw to the adapter (numbers, dates): formatting and plurals are the translation's business. A value
    that drives a plural is named `count`.
  - Except a value ICU cannot format (a file size with its unit chosen by magnitude, a list): the library formats it in
    the adapter's locale (`Intl`) and passes it as a string, which the translation only places (`{size}`).
- The translations: ICU messages as JSON, one file per language, `locales/<language>.json`, derived from the English
  functions, with a test that their keys and placeholders match. No ICU (or other message format) implementation in
  the package: the app's i18n renders them.
  - `en.json` too (American English, the default's texts), so the app's i18n knows every key. Another variant
    (`en-GB`, `de-CH`) only for keys whose wording differs.
  - Exported as they are, by a subpath: `"./locales/*.json": "./locales/*.json"`. The app knows the namespace and the
    languages itself.
  - An app without ICU translates in its own format, or keeps English.
- How the app looks up a text is its own business. An example with i18next and `i18next-icu`, the library's files
  loaded on demand:
  ```ts
  i18n.use(ICU).use(resourcesToBackend((language: string, namespace: string) =>
    namespace === 'formValidation'
      ? import(`@scope/form-validation/locales/${language}.json`)
      : import(`./locales/${language}/${namespace}.json`)
  ));

  const i18nAdapter: I18nAdapter = {
    currentLocale: () => i18n.language,
    // `exists`: `t()` gives the key itself when there is no translation.
    // `null`: the app's default namespace (`defaultNS`).
    translate: (namespace, key, params) => {
      const ns = namespace ?? undefined;
      return i18n.exists(key, { ns }) ? i18n.t(key, { ns, ...params }) : null;
    },
    // `loaded`: the library's files arrive later.
    onChange: (listener) => {
      i18n.on('languageChanged', listener);
      i18n.on('loaded', listener);
      return () => {
        i18n.off('languageChanged', listener);
        i18n.off('loaded', listener);
      };
    },
  };
  ```
- Never name a specific i18n library in the package's code, docs or specs, except i18next and react-i18next as the
  example.
- A clash of a package's namespace with an app's own is solved in the app's adapter (e.g.
  ``ns: `components.${namespace}` ``).

## Components built on i18next

For components meant for apps with i18next and react-i18next.

- They use the app's instance (`I18nextProvider`).
- i18next always with ICU (`i18next-icu`): the package's texts are ICU messages (`{name}`, `{count, plural, …}`), never
  i18next's own format (`{{name}}`, `_one`/`_other` keys). So the ICU messages of the components without an i18n
  library load into the same instance.
- i18next's types cannot check the params of ICU messages (`{name}` is not its `{{name}}`), so a missing or
  misspelled param is no `tsc` error. Therefore:
  - A message and every call of it change together, in the same step: the params by name, all of them, nothing else
    (`t('leave.workingDays', { count, days })` for `{count, plural, …} {days}`).
  - Every translation has exactly the placeholders of the English message, and the same plural argument.
  - After a change of messages, search the calls of every changed key and check their params.
- The package's texts (English and German) are i18next resources it exports (e.g. `dataTableTexts`), under its
  namespace; the app adds them to its instance: `resources: { en: { dataTable: dataTableTexts.en }, … }`.
- The package reads them typed by its own keys, not through the app's declared resource types (i18next's
  `CustomTypeOptions`): an app that types its own resources need not list the package's (e.g. a `useTexts()` hook of
  the package).

## Both

- The namespace of a package: its name in camelCase, no prefix: `'dataTable'`, `'fileUpload'`.
- An app's own keys: camelCase, separated by dots (`home.attention.allGood`).
- A library's keys: flat camelCase, no dots, prefixed by the part or area they belong to (`searchPlaceholder`,
  `headerBack`, `loginOr`); the library's own general texts without a prefix (`loading`, `retry`). Its JSON is loaded
  into the app's instance, and a dot means a path there (i18next's `keySeparator`): a flat key with dots is not found
  with the default separator, a nested one not without it (`keySeparator: false`). Flat keys without dots work with
  both.
